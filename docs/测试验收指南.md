# 金榜业务测试与验收指南

版本：V1.0　日期：2026-10-21　适用对象：测试人员、投标业务人员、商务与技术复核人员、环境管理员。

2026-10-22 补充：本机的“演示企业（模拟数据）”及流程演示项目只用于演练，输入采用人工确认模拟 TRM，附件为显式模拟说明页。不得将其导出成功或零待补充结果计入独立解析准确率、真实证据完整性、真实业务人员验收。正式验收继续使用冻结的真实样本及有出处的企业资料。

新增回归项：待审核人员和业绩不得进入文件；自动财务选最近三个独立审计年度；长期证照与查询时点材料不需虚构到期日；三证合一、开户证明、三类信用查询附件进入相应章节；同名 PDF/Word 原稿避免重复误报；本包选材必须隔离，修改后旧文件失效；取消必需检测报告后资格审查仍应阻断；演示 Word 和 PDF 每页保留模拟标识。仍应对导出的每节每页逐项检查。

本轮验收要形成三类可以追溯的证据：**机器解析与独立人工基准的差异、生成成品逐节逐页的检查结果、真实业务人员从导入到导出及终审的完整操作记录**。测试通过不以“按钮都点过”“自动化测试全绿”或“文件能下载”为依据。

操作方法可参照 [用户使用手册](Jinbang用户使用手册.md)；原计划指标见 [原型开发计划](原型开发计划.md)。本指南中的记录表统一在 [测试验收记录模板](测试验收记录模板.md)，每轮复制一份填写。

## 1 本轮交付物与验收条件

| 验收项 | 必须提交的材料 | 判定口径 |
|---|---|---|
| 解析准确率 | 冻结样本清单、双人标注与裁决记录、人工基准、原始机器 TRM、逐字段对比表、统计报告 | 原计划目标为字段级准确率不低于 90%，单批次解析不超过 5 分钟；本指南第 4 节统一计算方法 |
| 成品质量 | 招标要求到生成章节的对照表、每份文件的逐页检查记录、问题截图、修复前后版本、复核签字 | 每个必需章节与每一页均有记录；零项未关闭的阻断或重大缺陷 |
| 业务全流程 | 参与者与前置资料、分步时间、操作录像或截图、项目及任务 ID、所有人工帮助与返工、最终文件清单、业务人员结论 | 原计划目标为未参与调试标包从导入到导出不超过 40 分钟；另列人工终审完成时间，不能混为同一指标 |

本轮建议增加以下发布门槛，由测试负责人和业务负责人在开测前签字冻结：关键字段全部正确；关键字段无无依据新增值；保留样本中的每个包均达到准确率目标；商务与技术成品均通过；未见标包操作不依赖研发代办。未冻结门槛时报告原始结果，不事后选取有利标准。

“关键字段”至少包括：批次与分标包身份、投标截止与开标时间、资格硬条件、最高限价及金额单位、评分权重、全部 ★ 参数、必需递交文件及渠道。未达到门槛时保留实测结果，不以平均值或人工修正后的结果替代。

## 2 人员分工与执行顺序

| 角色 | 职责 | 独立性要求 |
|---|---|---|
| 测试负责人 | 编号、冻结样本与版本、组织执行、汇总缺陷与报告 | 不替业务人员作正确性判断 |
| 标注人 A 与 B | 从原始招标材料独立建立基准；核对文件、条款和表格位置 | 冻结前不查看系统解析结果，不互相抄录答案；研发不能充当唯一标注人 |
| 业务裁决人 | 处理标注分歧，确认业务含义与文件适用关系 | 不根据机器输出改写标准答案 |
| 业务操作人 | 按正常投标工作方式完成整个流程 | 使用独立成员账号；正式场次不能参与过目标标包的开发调试或演练 |
| 商务与技术复核人 | 检查生成章节、证据、参数与版式 | 尽量与操作人分开；分别签字，不以系统“满足”代替复核 |
| 环境管理员 | 确认版本、准备账号、保全快照及定位故障 | 协助必须记录；不能静默改库、改 TRM 或代替操作人完成任务 |

执行顺序：**冻结环境与样本 → 只看原文建立人工基准 → 冻结基准 → 保存机器原始结果并对比 → 使用确认版进行生成 → 检查每节每页 → 未见标包独立操作验收 → 汇总与签字**。

已知样本可用于熟悉界面和回归。正式未见场次开始前，操作者不得提前查看目标标包的解析结果、生成文件或专项操作答案。业务标注人员可先标注，但不向操作者透露系统问题和绕行方法。

## 3 开测准备

### 3.1 环境与版本冻结

当前本机访问地址为 `http://localhost:8080`。其他电脑的 `localhost` 指向自己，联机测试由管理员另提供宿主机局域网地址。每位人员使用独立测试账号，首次改密、通用培训和浏览器设置在正式计时前完成。

管理员执行以下只读命令，并把输出保存在受控测试目录：

```bash
docker compose ps
docker compose images
docker compose config --services
git rev-parse HEAD
git status --short
curl --fail http://localhost:8080/api/health
```

另记录 API、worker、web 的实际镜像 ID：

```bash
docker inspect --format '{{.Name}} {{.Image}}' $(docker compose ps -q jb-api jb-worker jb-web)
```

**Git 提交号不等于容器版本。** `docker compose up -d` 会使用现有镜像，未必包含工作区最新代码。管理员须提供镜像来源或构建记录，说明 API 与 worker 是否同一代码版本。不能确认时标记“镜像来源未核实”，本轮只能证明该镜像的表现；需要测试最新修复时，由管理员另行安排构建后重新冻结版本。测试期间不重建或替换镜像。

记录浏览器、操作系统、Word/WPS 及版本、时区 Asia/Shanghai、LLM 开关及模型、评分模板与否决规则配置、PDF 转换是否可用。只记录密钥“已配置/未配置”，不要保存密码、令牌、完整环境变量或展开后的 Compose 配置。

开测前确认 API 和 worker 正常、页面可登录、上传及文件下载可用。有 PDF 验收要求时先转换一份非正式演练文件验证；仅存在 gotenberg 容器不代表 API 已接通转换服务。未提供 PDF 时必须在范围中写明，不将桌面软件另存的 PDF 算作系统 PDF 导出通过。

### 3.2 样本与资料冻结

由测试负责人建立样本清单。建议首轮覆盖以下六组，每组指定批次和目标标包，不只记 ZIP 文件名：

| 样本组 | 用途 | 选择要求 |
|---|---|---|
| 物资主线 | 已知回归 | 陕西样本，覆盖综合网管、UPS、模块化数据中心等不同参数结构 |
| 物资变体 | 已知回归 | 信通中心或另一种已支持物资文档结构 |
| 服务公开招标 | 已知回归 | 江苏包 147/148，含可参考的历史成品 |
| 服务竞争性谈判 | 已知回归 | 福建样本，覆盖采购/应答术语、评分细则附件；以实际文件中的包号为准 |
| 未见物资标包 | 独立验收 | 未参与开发、调试、演练，记录由谁确认未使用过 |
| 未见服务标包 | 独立验收 | 同上，与未见物资分别出结论 |

没有未见样本时可完成已知样本回归，但“泛化验证”和“未见标包全流程验收”均标记未完成，不能用已知样本替换。六组是首轮覆盖方案，不代表对所有国网文档变体的统计保证。

每组资料包含：原始 ZIP、全部适用公告与澄清补遗、正式发布顺序、目标包、企业档案快照和附件、可用产品及证明资料。记录 SHA-256、大小、文件数或页数；归档样本使用其原有业务日期核验，当前已过截止日不自动认定为解析错误。

历史成品只用于辅助理解章节和版式，**招标文件、适用澄清与企业真实证据才是标准答案的来源**。不能要求系统复刻历史成品中的错漏。

样本与客户资料只存放在公司受控目录，不复制到 `docs/`、`tests/` 或提交到 Git。本文及空白模板可以入库，填写后的记录、截图、原始 TRM、成品和录像不得入库。未经授权的外部 LLM 不参与敏感资料测试。

### 3.3 准备正式操作场次

先冻结满足所选标包要求的企业档案及证明资料，由业务负责人核实资料确实可用；不得为了清零待补充编造资质、参数或承诺。另准备一份有已知缺口的档案用于阻断测试。

正式场次使用完整档案；缺口场次单独编号。企业建档、证据整理等准备时间单独记录，不计入“已准备资料前提下的 40 分钟”，但必须在报告中披露。正式过程中新发现缺资料并补录、返工和等待仍计入场次时间。

## 4 独立人工标注与解析准确率

### 4.1 建立和冻结人工基准

1. A、B 分别解压并阅读原始文件，先列出实际包含的分标包、文件及规范书关系。
2. 两人独立标注全部关键字段与重复表格，记录原文、文件相对路径、条款/表格/行列。Word 页码会随版本变化，必须同时提供可搜索的原文或条款号；xlsx 记录工作表和单元格。
3. 按本节字段目录标注普通字段。首轮关键字段和所有目标列表全量标注，不从机器已抽出的行反向挑选。
4. 对齐两份基准，保留两人的原始答案及分歧。裁决人按正式来源处理分歧；来源冲突且无法确定的标“待裁决”，不能凭经验猜测。
5. 冻结 golden 版本、哈希、计分字段范围、关键字段集合及别名映射。之后才允许比较机器输出。计算“裁决前一致率＝两人相同结论的条目数/双人共同标注条目数”，同时报告分歧数与最终裁决依据。

确需修正基准时另建版本，写明原文证据与理由，并对全部受影响样本重算；不得只改失败项使机器通过。已用于修复的保留样本转为回归样本，下轮独立验收须换新样本。

### 4.2 标注字段目录

以下路径按当前 TRM 模型描述。数组下标仅用于找到输出；人工比较必须用“样本＋分标＋包＋条款/规范书＋原始行”等业务身份，不以数组顺序判定对应关系。

| 对象 | 计分内容 | 原文定位依据 |
|---|---|---|
| 批次 | `batch_name`、`batch_no`、`terminology`，包清单完整性 | 公告、主文件及目录 |
| 关键条件 | `key_terms` 下的截止、开标、澄清时间，有效期，保证金模式，签章、纸质接收、电子投标要求，限价及税率说明 | 公告及前附表；明确原文、归一值和单位 |
| 包身份与范围 | `packages` 下的分标/包号、名称、项目单位、范围、预算、限价、工期、报价方式、联合体要求 | 本包需求表、公告、主文件 |
| 评审办法 | `scoring_ref` 的模板名、价格方法、系数、商务/技术/价格权重 | 前附表及需求一览表 |
| 前附表与否决项 | `prenotice` 的条款号、名称、内容；`rejection_rules` 的类别、方面、否决内容 | 原始表格逐条核对，包含例外及限定条件 |
| 递交方式 | `submission_table` 的文件类别、序号、项目、全部渠道、端口 | 第六章提交方式表 |
| 货物清单 | `materials` 的归属、项目、描述、数量、单位、交货时间地点、规范书 ID | 附件逐行、逐单元格核对 |
| 资格要求 | `qualification` 的业绩、年限、范围、报告、其他条件、代理商要求 | 资质业绩附件及服务需求表 |
| 技术规范 | `spec_docs` 的 ID、标题、来源、结构类型；`param_rows` 的名称、单位、需求值、★ | 规范书正文及参数表；不能将封面当正文 |
| 评分细则与格式 | `scoring_templates` 的名称、类型、来源、要素、标准及上下限；`format_blocks` 的标题和必需格式内容 | 本包正式附件、第六章 |

派生计数、告警、来源标记和重复展示可单列检查，不作为增加主准确率分母的条目。相同事实的原文与归一值指定一个主要计分项，其余作为证据，避免重复计分。`param_rows.response` 是后续投标响应，不混入原始招标需求解析准确率。

只给模板名称而未附细则时，名称可以计分，不能凭其他标包的细则补出标准答案。服务类叙述式规范没有标准参数表时，记录“不存在该表”，不人为制造参数行。

### 4.3 标注状态与等价规则

| 基准状态 | 含义 | 如何计分 |
|---|---|---|
| 有明确值 | 原文直接给出，或有明确可追溯的换算关系 | 纳入应抽取字段数 N |
| 明确不存在 | 已检查适用来源，该条件或表格确实没有 | 单列空值/误报检查，不用大量空值抬高主准确率 |
| 不适用 | 本包业务不涉及该字段 | 排除，记录理由；输出不应虚构适用要求 |
| 待裁决 | 来源冲突或无法可靠确定 | 单列数量及占比；关键项未裁决前不能出通过结论 |

忽略无意义空格、换行、全半角和等价的日期显示。金额、百分比、数量、单位及“至少/不超过/不得”等方向不能丢失。“90 日”与数值 `90` 可等价；“不少于 3 项”与“不超过 3 项”不等价。原文没有结论时 `null` 不等于 `false`，“未说明保证金”不等于“不需要保证金”。

语义等价由复核人按完整条件判断，不能只看关键词或由同一个 LLM 自评。规范书或条件串到其他包，即使文字相同，也不算本包正确。对所有错误记录类型：漏抽、错值、截断、条件反向、单位错误、错误归属、重复、无依据新增。

### 4.4 保存原始机器结果

由管理员先保存任务解析完成、尚未经人工修改的原始 TRM，命名包含样本 ID、项目 ID、时间及模式。HTTP 的 `GET /api/projects/{id}/trm` 是原始机器版；`?confirmed=true` 在没有确认版时可能回退机器版，必须结合项目 `confirmed` 状态判断，不能仅按 URL 标记为人工确认版。

前端不保证有 JSON 导出按钮。管理员可按附录通过已登录浏览器只读下载。标注人冻结前不得查看快照。确认页有些字段只读，无法在界面修正时记为“纠错能力缺口”；接口或开发介入的修正另行留痕，不能算业务人员独立完成。

基线使用自动上传解析结果；LLM 开关按实际功能分别登记。资格自检中的 LLM 增强不能冒充初次上传的解析结果。若补测 CLI/接口增强，分别保存输入输出、版本、耗时与模式，不覆盖基线或合并统计。

### 4.5 计算与报告

一个计分项是一条事先冻结的**字段实例**，例如“某分标包、某规范书第 7 行、需求值”。对每个应抽取项只分配一次：正确 C、错值 W、漏抽 M。原文有值而机器为空或未生成相应行，记 M；有对应项但内容错误记 W。故 `N=C+W+M`。

机器输出的无依据新增字段实例记 X，包括多出来的行、重复行的非空计分字段、凭空增加的条件，以及基准明确不存在却填出的事实。错误替代值已记 W，不再重复记 X；多出来的列表行按与基准相同的字段目录逐字段记 X，不能一行只算一个额外项。包或行身份无法对齐的输出不能因“看起来相似”直接接受，应裁决其归属并记录遗漏与新增。

本轮将原计划“字段级准确率”操作化为以下统一口径，并在开测前冻结：

- **主准确率 A＝C/(N+X)**：新增幻觉也进入分母；目标不低于 90%。
- **正确抽取覆盖率 R＝C/N**，**输出精确率 P＝C/(C+W+X)**，同时报告，不用其一替代 A。
- **关键字段准确率 Ak＝Ck/(Nk+Xk)**：本轮建议门槛 100%，且关键项 Xk 为 0。
- **明确不存在字段的空值正确率**单列，分母为该类基准项数；输出有值的误报同时进入 X。
- 任一分母为 0 则记“不适用”，不能写为 100%。待裁决、不适用、排除项均单列数量和原因。

例：100 项应抽取事实，90 正确、6 错值、4 漏抽，另有 5 项无依据新增，则 R=90%，P=90/101≈89.11%，**A=90/105≈85.71%，未达到 90%**。人工修正后全对不能改变这一轮机器分数。

列表另报预期行数、匹配行数、漏行、多行、重复行和包归属错误。每个样本、每个包、每类字段、关键/普通字段、物资/服务、已知/未见、确定性/LLM 模式分别统计；既给合并计数后的总分，也给各包分数的简单平均和最低分。批次共用字段只计一次，包级报告中注明引用，不重复摊入总体。

全量标注就报告全量。若后续轮次只抽查普通字段，必须在看输出前确定分层规则、抽样数量和随机种子，保留抽样清单，注明“抽样准确率”；关键字段与 ★ 行仍全量。不得把便利抽样或只抽成功页的结果外推为全项目准确率。

## 5 生成文件逐节逐页验收

### 5.1 冻结检查对象

分别保存原始机器 TRM、业务确认 TRM、企业档案与附件快照、生成任务/版本 ID、规则和模板配置、草稿、正式 Word、系统 PDF 及其哈希。验收绑定“某次生成的某个文件”，不能只写“技术文件已看”。

第一次生成若被阻断，先保存草稿及缺失项，做阶段性检查；补齐后重新生成、审查，再检查正式件。两次文件必须分开记录，不能把两版正确章节拼成一次通过。

### 5.2 先逐节检查内容

商务和技术复核人先独立从招标原文建立“要求 → 应有章节/附件 → 生成位置”的完整对照，再检查产出。不能以生成文件现有目录作为唯一检查清单。

| 检查对象 | 必查内容 |
|---|---|
| 文件组成 | 商务/技术/价格及工具内填报项目是否完整分工；系统未产出的价格文件另列责任人，不假定已生成 |
| 封面及投标身份 | 企业名、项目名、批次、分标、包、日期及投标/应答术语正确，无其他客户或标包残留 |
| 必需表单与承诺 | 第六章格式项逐一对应，必需语句、表头、说明、授权人和签章位置未丢失或误填 |
| 资格与证明 | 每项要求有对应证据，编号、日期、适用型号/人员、最终用户及有效期一致；附件清晰且属于本企业 |
| 技术响应 | 全部需求逐条覆盖；★ 项逐项核验；数值、单位、范围、方向与原文一致；保证值来自产品或报告；真实偏差未写成“无偏差” |
| 方案与评分 | 覆盖正式评分要素；人员、案例、证照、数字和承诺均有证据；引用 ID 存在并实际支持结论，不能只核对引用标记 |
| 多包隔离 | 分别核对至少两个包的封面、关键参数、业绩、母版和附件；重号包必须连同分标识别 |
| 递交要求 | 文件类别、渠道、端口、格式、大小及需在官方工具补做的项目与招标原文一致 |

每个必需项填写生成页码、检查结果与证据。缺一节即记录缺陷；没有适用要求的项目写“不适用＋原文理由”，不能空着。

### 5.3 再逐页检查版式与可读性

1. 在实际计划使用的 Word 或 WPS 打开每个完整 Word 文件，记录软件版本、总页数及是否报修复错误。
2. 全文搜索“待补充”“需核实”“XXX”等占位和模板提示，检查页眉页脚、文本框、嵌套表格与隐藏内容。不能只以工作台待补充数量为准。
3. **从第 1 页到最后一页逐页登记，每页一行**。检查标题层级、目录与页码、表格跨页和续表、重复表头、页边距、溢出/裁切/重叠、乱码、空白页、图片清晰度和比例、签章区域、脚注及页眉页脚。空白页也登记并判断是否合理。
4. 图像证据须能辨认关键名称、编号、日期和印章。针对合同/报告检查附件顺序、完整页数、是否倒置以及是否错挂。
5. 检查批注、修订、隐藏文字、作者等属性及模板残留；系统“元数据已清理”提示不能代替检查。确需签章或工具处理的步骤单独记录。
6. 有系统 PDF 时，在固定阅读器检查其**每一页**，核对对应章节、表格、图片、数字及页数变化。页码不一致可以是正常重排，但必须逐项定位确认无缺失、截断或错序。
7. 未提供系统 PDF 时，记录 PDF 验收“未完成/阻塞”。可另存 Word 渲染 PDF 辅助核查，但命名“人工转换参考”，不得标为系统导出件。
8. 使用对照表确认总页数＝已登记页数。不同软件页数不同，分别写明文件哈希、软件和各自总页数；不能混用页码。

布局缺陷截图应包含页码、上下文和异常区域；内容缺陷同时附原文定位与证据文件位置。修复后若文档重排，重新覆盖新版本所有页，不能只复查旧页码。

### 5.4 判定与外部修改

| 等级 | 示例 | 关闭要求 |
|---|---|---|
| P0 阻断 | 串包/串企业材料、关键金额或参数错误、编造资格事实、必需文件缺失、错误正式导出 | 修复后重新生成、审查并复验受影响内容；未关闭不通过 |
| P1 重大 | 必需章节或证据缺失、★ 未响应、关键表格被裁切、重要扫描件不可辨认、流程必须研发代办 | 关闭并由对应商务/技术负责人确认；未关闭不通过 |
| P2 一般 | 不影响含义的局部样式不一致、非关键排版问题 | 记录并修复；若延期，须逐项注明影响、负责人和业务接受意见 |

Word 下载后人工修改的文件另存新名称及哈希，记录修改人、范围和用时。当前流程不能默认将外部编辑文件重新作为同一已审查版本导入。**原系统的审查/导出通过不覆盖外部修改件**；外部版本须重新人工终审，并报告人工工作量。不能用外部修好的文件反向证明系统原始成品通过。

## 6 真实业务人员全流程记录

### 6.1 场次与计时规则

至少安排两个独立正式场次：未见物资包、未见服务包各一个。优先由两位真实标书人员分别操作；只有一人时如实披露，不声称验证了多人可用性。研发只观察，测试人员计时并记录。

操作人可阅读通用手册和招标原文；观察者不提示下一步、正确字段或绕行方式。业务咨询、管理员介入、研发代办都按发生时间记录，区分“正常业务确认”和“为绕过系统缺陷提供帮助”。后者不能记为独立完成。

统一记录下列时间点，使用带秒数的 Asia/Shanghai 时间，同时保存截图或录像时间轴：

| 时间点 | 定义 |
|---|---|
| T0 | 操作人第一次开始上传正式场次的招标 ZIP |
| Tp | 任务显示解析完成，原始 TRM 可读取；解析耗时另按解析任务 queued/running 到 done 的时间记录，注明是否含排队 |
| T1 | 目标包所有范围内文件完成系统正式导出，并成功下载；只生成草稿、审查标签通过或只导出商务文件均不到 T1 |
| T2 | 商务与技术逐节逐页终审完成，阻断和重大问题均关闭；有外部返工则采用最终人工版本的完成时间 |

- 原计划 40 分钟指标记作 `T1−T0`，包含上传、等待、查原文、补录、失败、重试、重新生成与导出下载。
- 业务就绪总耗时记作 `T2−T0`，人工终审及外部整理耗时另列；不能因 T1 小于 40 分钟就宣称“40 分钟可正式递交”。
- 正式场次前的登录、培训、企业初始建档单列。网络中断、离席等暂停记录起止与原因，主报告保留墙钟总耗时；可另报扣除暂停时间，不能只展示扣除后的数值。
- 首次尝试和复测分别编号，不能把练熟后的最快一次当首次成绩。系统阻断且无法继续时记录终止时间与原因，该场次不能算导出完成。

### 6.2 操作与留证步骤

| 步骤 | 操作人执行 | 观察者记录与检查 |
|---|---|---|
| 1 导入 | 上传冻结的原始 ZIP，等待解析 | T0、上传及任务时间、文件哈希、项目与任务 ID、失败重试 |
| 2 核对项目 | 核对包清单、截止、开标时间和警告 | 错值/缺值、是否找到编辑入口、人工补录分钟数 |
| 3 确认 TRM | 对照原文核对关键条件、各包、资格、★ 项、递交方式，保存人工确认版 | 保存前后快照、修改清单、只读无法纠错项；不能先改再测解析分数 |
| 4 资格自检 | 选本次企业，运行自检并逐包看证据 | 预期结论由业务事先给出；错判、风险提示及 LLM 状态，决定是否继续 |
| 5 生成 | 选择正确包，按冻结模式生成商务与技术文件 | 生成任务 ID、是否为母版/降级、待补充与真实偏差、等待时间 |
| 6 整改复查 | 按实际来源补资料，重新生成和审查 | 每轮变化及人工操作、阻断是否解释清楚、重跑次数；不删除占位文字骗过检查 |
| 7 评分与递交 | 看模拟评分和依据，对照第六章核对矩阵 | 有模板按模板核验，无细则不得臆定评分；系统未产出及工具内填报内容单列 |
| 8 正式导出 | 导出并下载本包全部范围内文件 | T1、文件哈希和版本、Word/PDF 实际产出、未完事项 |
| 9 人工终审 | 按第 5 节检查所有章节与页面 | T2、商务与技术签字、外部修改及用时、最终风险 |
| 10 反馈 | 独立评价是否愿意用于下一次业务 | 最困难步骤、误导提示、还需什么资料与功能；不要由研发代填结论 |

发现企业本来就不满足资格时，正确结果可以是“不可投/风险明确”，但该场次不计为成功完成文件交付。正式端到端场次需换用真实满足要求的测试资料并另开记录，不虚构事实继续通关。

测试只验证到系统导出及人工终审，**不向真实 ECP 提交**，不把项目人为标记“已递交”当作完成官方递交。签章、加密、官方工具填报与回执若另行演练，必须单独列范围和证据。

### 6.3 观察记录补充

记录每个步骤是否首次找到入口、是否误选企业/包、错误提示是否能指导整改、刷新后结果是否可恢复、失败后是否丢失输入、是否依赖技术人员。系统时间线只是一部分证据，不能替代查阅原文、外部编辑、人员帮助与暂停记录。

## 7 导出门禁与变更失效专项

下列测试在独立测试项目/企业副本执行，每项从“已满足其他条件”的基线开始，只改变一个因素。规则配置可能影响全部项目，由管理员安排独占时段执行并记录恢复，不在正式计时场次中途变更。

| 编号 | 操作 | 预期与留证 |
|---|---|---|
| G01 | 未确认 TRM，尝试审查和正式导出 | 明确阻断，保存原因；草稿可下载不等于正式导出成功 |
| G02 | 使用缺少确实必需资料的档案生成，再尝试正式导出 | 待补充显示、缺口可定位，正式导出被阻断 |
| G03 | 用真实可识别的否决条件触发审查，例如按开标日过期的证照 | 否决原因与证据匹配，正式导出被阻断；不能把“未触发”直接归因资料不全 |
| G04 | 在专用测试副本调整规则配置 | 旧审查失效，要求按新配置复查；恢复配置后也重新核验 |
| G05 | 已导出后修改企业资料、附件或确认 TRM | 旧审查/导出失效，旧正式下载被阻断；重新生成、审查后恢复。每种变化单开子用例 |
| G06 | 同一分标或不同分标含相同包号，分别生成审查 | 结果、原件和文件不串用；不能用 A 包审查放行 B 包 |
| G07 | 再次生成后尝试旧正式链接 | 旧版本不可继续作为当前有效正式件下载，新版本需重新审查 |
| G08 | 生成后刷新或重新登录 | 最新文件、任务与审查信息可识别并恢复，仍对应正确企业与包 |

界面没有入口的负向操作由管理员使用受控接口执行，单列技术专项，不伪装成业务人员独立操作。实际镜像未实现预期时提交缺陷，不能因为仓库有对应测试就直接勾选通过。

## 8 证据保存与缺陷复测

建议受控测试目录结构如下，填写后的内容不放代码仓库：

```text
验收批次/
  00环境与范围/
  01样本与哈希清单/
  02人工基准/A标注 B标注 裁决 冻结版/
  03原始机器TRM与逐字段对比/
  04确认TRM与档案快照/
  05生成版本与章节逐页记录/
  06场次计时截图录像/
  07缺陷与复测/
  08验收报告与签字/
```

每项缺陷必须能回答：哪个镜像版本、样本、企业、分标包、项目和任务；输入前提；复现步骤；预期与实际；原文依据；影响；截图/文件位置；严重程度；负责人；复测结果。只写“解析不准”“排版不好”不能关闭问题。

复测保留原失败证据。代码/镜像、规则、模板、档案或 golden 任一变化，都建立新运行编号并记录差异。修复只改变部分模块时也要复验受影响下游：解析变化需重做确认与生成，生成变化需重做审查与成品检查。修改标包后不能继续沿用旧页码、哈希或签字。

## 9 最终报告与签字

测试负责人按以下顺序出具结论：

1. 版本、样本覆盖和人员独立性；未见样本是否仍保持未参与调试。
2. 解析 N/C/W/M/X、A/R/P、关键字段、列表完整性、每包/每类分数、待裁决与排除项、解析用时。
3. 商务/技术每节覆盖、每页覆盖、Word/PDF 检查、证据缺口、P0/P1/P2 数量及关闭状态。
4. 每个正式场次 T1−T0、T2−T0、人工修改时间、帮助次数、首次成功率；失败场次也纳入汇总。
5. 三项分别给“通过/不通过/阻塞未完成”，写出未验范围、遗留问题、业务可接受范围及下一轮条件。不能将“无法测”写成“不适用”规避验收。

测试负责人签数据完整性，业务负责人签适用性，商务与技术复核人签成品内容及质量；研发只签缺陷修复情况。无签字、缺未见样本、关键项待裁决或存在未关闭 P0/P1 时，不出具“可用于正式投标”的结论。

## 附录 管理员保存只读项目快照

管理员在已登录系统的浏览器中进入目标项目，打开开发者工具的 Console，确认当前域名为测试系统后运行以下脚本。输入项目 URL 中的 ID。脚本只读取数据并下载本地 JSON，不修改项目；只在授权测试机器上使用，生成文件按客户资料管理。

```javascript
(async () => {
  const id = window.prompt('请输入目标项目 ID')?.trim()
  if (!id) return
  const token = localStorage.getItem('jb_token')
  if (!token) throw new Error('请先登录测试系统')
  const base = `/api/projects/${encodeURIComponent(id)}`
  const read = async (url) => {
    const r = await fetch(url, { headers: { Authorization: `Bearer ${token}` } })
    if (!r.ok) throw new Error(`读取失败 ${r.status} ${url}`)
    return r.json()
  }
  const detail = await read(`${base}/detail`)
  const machineTrm = await read(`${base}/trm`)
  const confirmedTrm = detail.confirmed ? await read(`${base}/trm?confirmed=true`) : null
  const tasks = []
  for (const task of detail.tasks ?? []) {
    tasks.push(await read(`/api/tasks/${encodeURIComponent(task.id)}`))
  }
  const snapshot = {
    capturedAt: new Date().toISOString(), timeZone: 'Asia/Shanghai',
    projectId: id, detail, machineTrm, confirmedTrm, tasks,
  }
  const blob = new Blob([JSON.stringify(snapshot, null, 2)], { type: 'application/json' })
  const url = URL.createObjectURL(blob)
  const link = document.createElement('a')
  link.href = url
  link.download = `项目快照_${id}_${Date.now()}.json`
  link.click()
  setTimeout(() => URL.revokeObjectURL(url), 1000)
})()
```

分别在“解析完成尚未确认”“确认后”“生成审查后”“最终导出后”保存快照。保存期间暂停该项目的其他写入；多个接口不是同一事务快照，若期间发生变化应重新采集。脚本不会保存令牌，也不包含企业全部原始附件，企业资料与文件哈希仍需另行归档。不要提交包含请求头、令牌或下载鉴权参数的 HAR 或截图。
